리뷰어: Claude Fable 5.1 (brgr task `93dfa925`, revision 2). 대상: worktree HEAD `45407f9`. diff가 아니라 코드를 읽었다.

## 결론

- **P0(데이터 손실·잘못된 승인): 0건.** 읽은 범위에서 찾지 못했다.
- **P1: 1건, 재현했다.** 1차 발견 C3의 수정(#343)이 만든 회귀다. foreground `revise`가 끝나기 전에 죽으면 이전 revision의 실패 결과를 어떤 문서화된 명령으로도 확인 처리할 수 없게 되고, 배너와 그 revision의 worktree·브랜치가 영구히 남는다.
- **P2 코드: 2건.** `__notify` 디스패처가 지워진 홈을 되살리고 24시간 도는 것(이 머신에서 관찰, 요청 시 재현은 실패), 화면 규칙표의 continue-notice가 문장 속 문구에도 걸리는 것(읽기만).
- **P2 테스트: 실행으로 확인한 것 8건, 읽어서 확인한 것 6건.** 그 밖에 서브에이전트가 보고했고 내가 다시 확인하지 않은 것(표 33행)은 따로 두었다.
- **홈 탈출: 찾지 못했다.** 스위트를 격리 환경에서 1회 돌렸고, 스크래치 control home·`HOME`·`CODEX_HOME`·`CLAUDE_CONFIG_DIR` 어디에도 쓰인 것이 없었다. 실제 Herdr·`gh`·`claude`는 한 번도 불리지 않았다. 실제 `codex --version`만 10회 불렸다.
- **수정 12개(1차 발견에 대응한 11개와 #341):** 1차 발견에 대응한 11개는 원래 트리거를 닫는다(#338은 diff를 읽지 않고 테스트로만 확인). 회귀는 #343 하나를 찾았다. 7개는 되돌리거나 깨뜨리면 회귀 테스트가 실패하는 것을 직접 확인했다.
- 저장소는 건드리지 않았다(`git status --porcelain` 0줄, HEAD `45407f9`). brgr worker는 시작하지 않았다. brgr 명령은 모두 `--home <스크래치>`로 실행했다. 예외는 이 보고서를 봉인하는 `__seal-report` 한 번이다.

검토 방식: 항목 1(1차가 읽지 않은 코드)과 항목 3(수정)은 내가 직접 읽었다. 항목 2(테스트 약 3만 3천 줄)는 Opus 서브에이전트 7개에 나눠 읽혔다(Fable 아님). 그 결과는 내가 변이·실행·읽기로 다시 확인한 것만 발견으로 싣고, 나머지는 "재확인하지 않음"으로 구분했다.

## P1

### R1. foreground `revise`가 끝나기 전에 죽으면 이전 실패를 영영 확인 처리할 수 없다 (#343의 회귀)

- **위치:** `crates/brgr-cli/src/admission.rs:532-563`(`start_task(...).await?` 뒤에야 `acknowledge_previous`), `:1342-1351`(foreground는 `start_task` 안에서 실행 전체를 기다린다), `:1352-1361`(detached에서 supervisor 기동 실패 시에도 `Err`로 빠진다), `crates/brgr-cli/src/task_commands.rs:431`·`:450`(`result --ack`는 `latest_result`만 확인 처리), `admission.rs:620`·`:659`(`revise`도 최신 결과만 확인 처리 대상으로 잡는다)
- **트리거:** revision 1이 `failed`/`lost`로 끝난다. owner가 `brgr revise TASK … --foreground`를 실행하고, 그 프로세스가 실행 도중 죽는다(Ctrl-C, 호출한 에이전트의 도구 타임아웃, kill).
- **결과:** revision 2는 이미 admit됐으므로 이후 `result --ack`와 `revise`는 revision 2 이후만 본다. revision 1의 실패 결과는 확인되지 않은 채 남는다.
  - 그 owner의 모든 brgr 명령 끝에 `1 run(s) failed or were lost and are not acknowledged … Dismiss: brgr result TASK --ack`가 계속 붙는다. 안내된 명령으로는 지워지지 않는다. 작업을 accept한 뒤에도 남는다.
  - git 작업이면 `prune --apply`가 revision 1의 worktree를 `its failed result is not acknowledged; run brgr result <task> --ack`로 영구히 kept 처리한다. worktree와 `brgr/task-<short>` 브랜치가 남는다. 1차에서 고친 "worktree 영구 누적"과 같은 부류다.
- **#343 전에는** 확인 처리가 `start_task` 앞에 있어서 이 상태가 생기지 않았다(대신 C3가 있었다).
- **확인: 재현(직접), fixture 하네스, HEAD에서 빌드한 debug 바이너리, 스크래치 홈.** `run "SLOW" --deadline-seconds 2 --foreground --headless`(failed) → `revise … --foreground --headless`를 실행 중 `kill -9`(프로세스와 하네스) → `status`가 revision 2를 lost로 정리 → `result --ack` 두 번 모두 `acked result of revision 2 lost` → `revise`(revision 3, candidate) → `accept` → 배너에 revision 1의 `failed: attempt deadline elapsed`가 그대로 남았다. git 저장소로 같은 순서를 밟으면 `prune --apply`가 `{"kept":1,"removed":0}`과 위 이유를 냈다.
- detached 경로의 `spawn_supervisor` 실패 분기는 읽기만 했다.
