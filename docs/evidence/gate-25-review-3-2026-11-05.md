## P2 — 코드

### C1. #359의 정리(sweep)가 같은 revision 안의 이전 시도를 빼먹는다 — spawn 재시도 뒤 첫 실패는 영영 확인 처리되지 않는다 (R1과 같은 부류)

- **위치:** `crates/brgr-store/src/result.rs:268`(`r.revision < ?3`만 고른다), `crates/brgr-cli/src/task_commands.rs:431`·`:450-457`(`latest_result` 하나와 "이전 revision"만 확인 처리), `crates/brgr-core/src/execution.rs:132-141`(재시도 가능한 spawn 실패는 `commit_terminal_result`로 `failed` 결과를 남기고 retry를 허가), `crates/brgr-store/src/attempt.rs:694-698`(그 결과에도 inbox 항목과 완료 알림이 생긴다), `crates/brgr-cli/src/failure_banner.rs:38-58`(배너는 owner의 미확인 failed/lost를 revision·시도 구분 없이 센다)
- **트리거:** one-shot 하네스의 프로세스 spawn이 `EAGAIN`(사용자 프로세스 한도)·`EINTR`·`ETIMEDOUT`으로 실패한다(`execution.rs:194-207`). `run`의 `max_attempts`는 2라(`admission.rs:235`) 같은 revision에서 두 번째 시도가 이어진다.
- **결과:** revision 1에 결과가 둘 생긴다(시도 1 `failed`, 시도 2 최종). `brgr result TASK --ack`는 시도 2의 결과와 `revision < 1`만 확인 처리하므로 시도 1의 `failed` inbox 항목이 남는다. 그 owner의 모든 brgr 명령 끝에 `1 run(s) failed or were lost and are not acknowledged … Dismiss: brgr result TASK --ack`가 붙고, 안내된 명령으로 지워지지 않는다. 시도 2가 candidate라 accept하면 `revise`도 할 수 없어(다음 revision이 생겨야 sweep이 닿는다) 영구히 남는다. `revision_settlement`는 최신 결과만 보므로 prune은 막히지 않는다.
- #359 전부터 있던 구멍이지만, #359가 "이전 실패를 `result --ack` 한 번으로 정리한다"로 닫았다고 한 범위에서 빠졌다. 트리거가 드물어 P2로 둔다.
- **확인: 재현(store 수준 probe, 스크래치 복제본에 테스트 1개 추가. fixture·실제 에이전트 아님).** `claim_attempt` → `commit_terminal_result(Failed)` → `grant_pre_spawn_retry` → `claim_attempt` → `commit_terminal_result_final(Failed)` → `result --ack`가 부르는 두 함수(`acknowledge_bound(latest)`, `acknowledge_older_failures_bound(.., 1, ..)`) 뒤 `inbox(owner, false)`가 `[(1, Failed, "spawn: resource temporarily unavailable")]`를 돌려줬고 settlement는 `Acknowledged(Failed)`였다. **CLI에서 spawn `EAGAIN`을 실제로 일으키지는 못했다**(결정적으로 만들 훅이 없다).
