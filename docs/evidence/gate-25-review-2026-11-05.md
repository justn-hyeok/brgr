## P1

### F1. 저장소 하위 디렉터리에서 시작한 작업의 `--capture-diff`가 그 디렉터리 밖의 새 파일을 빠뜨린다

- **위치:** `crates/brgr-core/src/git_diff.rs:103-123`(untracked 목록과 intent-to-add), `:138-145`(diff는 `:(top)**`로 저장소 전체), `crates/brgr-cli/src/workspace.rs:641-647`, `crates/brgr-cli/src/admission.rs:197`
- **트리거:** `brgr run`을 git 저장소의 하위 디렉터리에서 실행한다(`--workspace` 기본값이 cwd다). worker가 그 하위 디렉터리 밖에 새 파일을 만든다.
- **결과:** `git ls-files --others`가 `-C <workspace 하위 디렉터리>`로 실행돼 그 아래의 untracked 파일만 나열한다. diff 자체는 저장소 전체를 보므로, 밖에서 **수정한** 추적 파일은 들어가고 밖에서 **새로 만든** 파일만 조용히 빠진다. 봉인된 `text/x-diff`가 worker의 변경 전체가 아닌데 candidate로 올라오고, `brgr diff`·`brgr apply`가 그 불완전한 패치를 쓴다.
- **확인: 재현(직접).** `repo1/sub`에서 `run "OUTSIDE …" --capture-diff --foreground --headless`. worker가 `../outside_new.txt`(신규), `../README`(수정), `inside_new.txt`(신규)를 썼다. 봉인된 diff에는 `README`와 `sub/inside_new.txt`만 있고, worktree의 `git status`는 `?? outside_new.txt`를 보였다.

### F2. 작업 단위 취소 파일이 남아 다음 revision을 시작 전에 취소시키고, 그 작업은 되살릴 수 없게 된다

- **위치:** `crates/brgr-cli/src/main.rs:123-125`(`runs/<task>.cancel`, revision 없음), `task_commands.rs:603`(쓰기), `supervision.rs:116`(유일한 삭제, 그 supervisor가 정상 종료할 때만), `crates/brgr-core/src/execution.rs:65-69`(시작 전 검사), `admission.rs:654-656`(cancelled는 revise 불가). 같은 파일을 `pane_adapter/lifecycle.rs:113-114`와 `supervision.rs:266`도 읽는다.
- **트리거:** supervisor가 죽은(크래시, 강제 종료, 재부팅) 작업을 owner가 `brgr cancel TASK` 한다. 복구가 그 revision을 `lost`로 정리하지만 취소 파일은 남는다. 실패 배너가 권하는 대로 `brgr revise TASK …`를 실행한다.
- **결과:** revision 2가 즉시 `cancelled: "cancelled before process spawn"`으로 끝난다. cancelled는 revise할 수 없으므로 그 작업은 끝이고 새 `brgr run`이 필요하다.
- **확인: 재현(직접).** 실행 중인 작업의 supervisor와 하네스를 `kill -9` → `cancel`(`cancel_requested`) → `status`가 `lost`로 정리(배너에 "Retry: brgr revise TASK") → `runs/<task>.cancel` 남음 → `revise … --foreground`가 `{"revision":2,"outcome":"cancelled","error":"cancelled before process spawn"}`.

### F3. worktree를 만든 뒤 실패한 `revise`가 그 작업의 이후 모든 `revise`를 막는다

- **위치:** `admission.rs:967-1005`(lock → `prepare_task_workspace` → `write_json_new` 990 → 기록 999-1005, 실패 시 정리 없음), `admission.rs:1139-1145`(일반 경로는 `?`로 반환. `discard`는 워크플로 경로 `1164-1175`에만 있다), `workspace.rs:654-675`(slug가 `<short>-rN`으로 고정이고 있으면 거절), `worktree_prune.rs:557-562`
- **트리거:** `brgr revise`가 worktree 생성과 admission 기록 사이에서 끝난다. (a) 프로세스가 죽는다(느린 `git worktree add`나 snapshot 중 Ctrl-C, kill). (b) 기록이 실패한다. admission 기록은 설계상 재시도하지 않으므로 store 쓰기 잠금이 5초 넘게 잡혀 있으면 실패한다.
- **결과:** worktree와 `brgr/task-<short>-rN` 브랜치(그리고 (b)에서는 `launches/<task>-rN.json`)가 남고, 다음 `revise`는 매번 `refusing to replace existing path …/<short>-rN for a task worktree`로 실패한다. `brgr prune --apply`도 그 디렉터리를 `no task revision was admitted in this directory`로 남긴다. 손으로 worktree·브랜치·launch 파일을 지워야 한다. 기존 테스트 `worktree_created_before_admission_is_preserved_and_not_reused`(`cli_contract.rs:7990`)는 작업 ID가 새로 생기는 `run`만 고정한다.
- **확인: 재현(직접), 두 가지로.** (a) `BRGR_TEST_EXIT_AFTER_WORKTREE=1`로 `revise` → 종료 코드 78 → 다음 `revise`가 위 오류. (b) 테스트 훅 없이, 다른 프로세스가 store에 `BEGIN IMMEDIATE`를 9초 잡은 동안 `revise` → `database operation failed: database is locked` → 잠금이 풀린 뒤의 `revise`도 같은 오류.

### F4. 작업 worktree 안에서는 cwd가 `BRGR_HOME`을(그리고 같은 값의 `--home`도) 조용히 이긴다

- **위치:** `crates/brgr-cli/src/worker_identity.rs:83-94`, `:99-109`, `main.rs:257`
- **트리거:** cwd가 어떤 control home의 `worktrees/<repo>/<task>`(`.brgr/tasks`가 있는 worktree) 안이고, `BRGR_HOME`은 다른 홈을 가리킨다. 예: worker나 사람이 worktree 안에서 `BRGR_HOME=<스크래치>`로 fresh-home 점검이나 스크립트를 돌린다.
- **결과:** 명령이 `BRGR_HOME`이 아니라 worktree가 속한 홈에서 실행된다. 경고가 없다. `--home X`를 직접 쳐도 `X == $BRGR_HOME`이면 무시된다. 읽기뿐 아니라 `run`, `harness add`, `config set`, `prune --apply`도 다른 홈에 쓴다. Codex 데몬이 `BRGR_HOME`을 잃는 경우를 위한 의도된 규칙이지만, 환경 변수를 명시한 호출자와 구분하지 못한다.
- **확인: 재현(직접).** 홈 `h1`의 작업 worktree 안에서 `BRGR_HOME=h2 brgr --json prune`이 `h1`의 worktree 5개를 나열했다. `--home h2`를 함께 줘도 같았고, worktree 밖에서는 `[]`였다.
- **이 검토 중 실제로 발생했다:** 서브에이전트 하나가 이 저장소 worktree에서 `BRGR_HOME=<스크래치> brgr errors preview`를 실행했고, 그 명령은 **실제 control home**을 읽었다. 읽기 전용 명령이고 서브에이전트는 쓰기가 없었다고 보고했다. 내가 따로 검증하지는 않았다.

### F5. 버려진 head 복구(`head claim --abandoned`)는 owner당 사실상 한 번만 된다

- **위치:** `crates/brgr-store/src/takeover.rs:348-361`(committed·resumed도 "열린 takeover"), `crates/brgr-cli/src/head.rs:404-481`(`claim_core`. 출력 `471-479`에 retire 안내 없음), `head.rs:502-512`(abort는 양쪽 세션만), `head.rs:514-526`(retire는 incoming 세션만), `task_commands.rs:731-741`(`bind` 거절), `takeover.rs:532-563`
- **트리거:** 세션 B가 `head claim TASK --abandoned`로 head를 가져온다. 이 명령은 `head retire`를 하라고 말하지 않으므로 takeover는 `committed`/`resumed`로 남는다. 이후 B도 버려지고(컨텍스트 소진이 핸드오프의 이유다) 세션 C가 같은 복구를 시도한다.
- **결과:** C의 `head claim --abandoned`가 `owner already has a non-terminal takeover`로 실패한다. `accept`는 다시 `head claim --abandoned`를 권하고(순환), `head abort`·`head retire`·`bind`는 모두 거절한다. 그 owner의 미결 candidate를 문서화된 명령으로는 누구도 결정할 수 없다. 죽은 세션 ID를 `--as`로 사칭해도 미결 결과가 있으면 `retire`가 `cannot go from committed to retired`로 실패한다. 사칭한 세션으로 owner 쓰기를 먼저 해야 풀린다.
- **확인: 재현(직접).** `sess-A` 실행 → `sess-B` claim(`committed`, epoch 2) → `sess-C`의 claim·accept·abort·retire·bind가 모두 위 오류로 거절.

### F6. 하위 디렉터리에서 시작한 작업의 worktree는 영영 회수되지 않는다

- **위치:** `workspace.rs:641-647`(workspace = `<worktree>/<상대경로>`), `worktree_prune.rs:557-562`(`task.workspace == worktree` 비교), `worktree_prune.rs:1404-1411`(`reclaim_task`)
- **트리거:** F1과 같다. 저장소 하위 디렉터리에서 `brgr run`.
- **결과:** 결정 뒤 자동 회수가 아무것도 하지 않고, `brgr prune`은 그 worktree를 `no task revision was admitted in this directory`(사실이 아님)로 영구히 kept 처리한다. worktree 디렉터리와 `brgr/task-*` 브랜치가 작업마다 쌓인다. 데이터 손실은 아니다. 2026-09-28에 P1로 기록한 "worktree 영구 누적"이 이 부류의 작업에 그대로 남아 있다.
- **확인: 재현(직접).** F1의 작업을 `accept`한 뒤에도 worktree가 남았고 `prune`이 위 이유로 kept를 보고했다.

### F7. 오류 메모의 이슈 본문이 경로, 저장소 디렉터리 이름, 작업 UUID, 사용자 이름 조각을 내보낸다

- **위치:** `crates/brgr-cli/src/error_memo.rs:471-496`(`normalize_token`), `:521-585`(`redact`, `mask_piece`, `mask_home`). 입력은 `pane_adapter.rs:789-793`의 "…without writing its report to {경로}"
- **트리거:** macOS 기본 홈(`~/Library/Application Support/brgr`, 공백 포함)에서 pane 작업이 report 없이 끝난다. 또는 `/private/tmp/…` 아래 workspace.
- **결과:** 단어를 공백으로만 나누고 `/`에서는 나누지 않으며, UUID는 조각 전체가 UUID일 때만 가린다. 그래서 sample에 `~/Library/Application Support/brgr/worktrees/<repo>/<slug>/.brgr/tasks/<uuid>-r1/report.md`가 그대로 남는다. `/private/tmp/claude-501/-Users-<이름>-…` 같은 경로는 전혀 가려지지 않는다. class도 공백에서 잘려 `…report to <path> Support/brgr/worktrees`가 되므로 같은 실패가 지문 두 개로 갈린다. 본문은 "home paths, ids … masked"라고 말한다. `AGENTS.md`의 Error Memo 계약(ids, paths 제거)과 어긋난다. 이슈 보고는 기본으로 꺼져 있으므로 켠 경우에만 밖으로 나간다.
- **확인: 서브에이전트가 발견, 내가 코드를 읽고 `errors preview`를 스크래치 홈에서 다시 실행해 위 두 sample과 class를 확인했다.** 그 ledger 항목은 서브에이전트가 실제 ledger에서 복사한 것이다.

### F8. 문서대로 한 체크섬 검증이 실패로 끝난다

- **위치:** `docs/guides/unsigned-distribution.md:10-11`, `.github/workflows/release.yml:165-169`
- **트리거:** 안내대로 `.tar.gz` 하나와 `brgr.spdx.json`, `checksums.txt`를 받고 `shasum -a 256 -c checksums.txt`를 실행한다.
- **결과:** `checksums.txt`는 모든 아카이브(macOS arm64와 Linux x86_64)를 나열하므로, 받지 않은 아카이브가 `FAILED open or read`가 되고 종료 코드가 1이다. 검증 단계가 모든 사용자에게 실패로 보인다.
- **확인: 서브에이전트가 공개 v2.15.19 릴리스 자산으로 재현했다. 나는 두 파일을 읽어 원인만 확인했고 다운로드는 하지 않았다.**

## 확인했고 결함이 아니었던 것

- **범위 G4, 릴리스 워크플로**(서브에이전트): CI 대기는 `--commit "$GITHUB_SHA"`와 macOS job 성공을 요구하고 실패·취소·누락에 닫힌다. 캐시 없이 빌드한다. smoke test한 아카이브가 그대로 올라간다. crate 게시 순서(protocol → runner → store → core → registry → cli)가 실제 의존 그래프에 맞는다. 이미 게시된 버전 건너뛰기가 실패를 가리지 않는다. `run:` 블록에 `${{ }}` 주입이 없고 권한이 좁다. 버전 표기 전부 2.15.19이고 실제 릴리스는 Latest다.
- **schemas ↔ wire 타입**(서브에이전트): brgr가 내보내는 바이트를 스키마가 거절하는 경우를 찾지 못했다.
- **prune의 삭제 안전성**(직접): 봉인된 패치와 바이트 단위로 같을 때만 강제 제거, ignored 파일 별도 검사, 브랜치 보존 검사, symlink·cwd·등록·잠금 검사에서 손실 경로를 찾지 못했다.
- **결정 경로**(직접): `record_decision_in_transaction`의 owner binding·digest·candidate 검사, `claim_attempt`의 재시도 규칙, `commit_terminal_result`의 원자성에서 문제를 찾지 못했다.
- 미답 질문이 candidate를 막는 것(`reference.md:218-219`)과 `cancel`이 `--tree` 없이도 하위 트리를 취소하는 것(`reference.md:213`)은 문서화된 동작이라 보고하지 않는다.
- Operating Contract 대상(worker 권한, 화면 응답)은 지시대로 발견으로 올리지 않았다.
