# brgr v2.15.8

Dynamic Workflows, first version. A JavaScript script, run by node under a brgr
driver, launches workers through the same delegation contract as `brgr run`, reads
their sealed results, and creates a later task that did not exist at the start.
Nothing the script sees is an accepted change; you still accept or reject each
sealed result.

## What you get

- `brgr workflow init` writes `brgr-workflow.mjs` (the SDK: `agent()` and
  `parallel()`) and an example. `brgr workflow run SCRIPT.mjs` starts the script as
  a detached driver and returns the run id at once. `workflow status`,
  `workflow resume`, `workflow cancel` inspect and control it.
- A step is one worker task launched with `brgr run --workflow RUN --step KEY`. The
  launch is idempotent: running it again returns the first task. A changed input
  under the same key stops with "diverged" instead of launching again. The run's
  `--max-parallel` is enforced in the store transaction that records the step.
- If the driver dies, `workflow resume` runs the script again from the top.
  Finished steps replay from the journal; a step whose launch outcome is unknown is
  not run twice.
- You get one notice per run state change (blocked, completed, failed, cancelled),
  delivered like a task completion notice. Step tasks send no completion push of
  their own.
- A worker's question blocks the run (it is not a result) until you answer it.

## Panes

Steps open TUI worker panes beside your pane when you start `workflow run` from a
verified Herdr pane; the pane is recorded and verified again at every launch.
Otherwise use `mode: "headless"` for steps. A Codex head currently needs
`mode: "headless"`, because a Codex pane is only known after the call ends.

## Verified

Fixture-harness tests with real node cover the completion criterion (a follow-up
task created only from an observed report), resume after the driver is killed,
blocking on a question, a failed worker, invalid options and a changed objective.
Two live runs with real Cursor Grok 4.6 workers (one headless, one in panes) ran
two parallel steps, branched on a report, created a third task and delivered the
run notice to the owner's Claude session. Not checked: a Codex head, and head
migration during a run.

## Not in this version

`pipeline()`, retries, per-step deadlines, TypeScript tooling, and head migration
during a run.

## Compatibility

Additive store tables (runs, steps, run notices); no migration. A new brgr can read
an old store. `brgr run` without `--workflow` behaves as before.
