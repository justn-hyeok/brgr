# brgr v2.15.21

A second review of the code found a regression in v2.15.20: a `revise --foreground` killed mid-run left a failure that no command could clear. This release fixes it, along with a five-second stall in `status`, `wait` and `watch`, and notice dispatchers that outlived their home.

This follows v2.15.20 on the same day.

## Before you upgrade

- **`brgr result TASK --ack` now also acknowledges older failed or lost results of that task.** It frees a task already stuck by the regression. It never touches an older candidate and records no decision.
- **A `revise` now acknowledges the failure it replaces as soon as the new revision is admitted**, before it runs. A revise refused before admission still leaves the failure unacknowledged.
- **`wait` and `watch` can take up to five seconds, not one, to report a run whose supervisor died.** A sealed result is still seen within 200 ms.
- **A line such as `Press Enter to continue or Ctrl-C to quit` is no longer answered with Enter.** A continue notice must be what the line says. Anything else is reported to the owner like any screen brgr does not know, and fails the run after three minutes.
- **An older revision's worktree now stays until the newest revision is settled**, and a later command reclaims it.

## What changed

- **Stuck failures (#359).** See above. After the regression, the banner told owners to run a command that could not clear it, and `prune --apply` kept the worktree and branch for good.
- **Five-second stall (#355, issue #352).** While a revised task ran, every `status`, `wait`, `watch` and Codex hook slept up to five seconds waiting for the newer revision's worker. Cleanup no longer waits. `accept`, `reject` and `result --ack` keep their wait for a worker that is exiting.
- **`wait` and `watch` CPU (#353, issue #351).** Recovery runs every five seconds instead of every second.
- **Notice dispatchers (#354, issue #350).** A dispatcher could recreate a deleted home's database and then run for 24 hours. It no longer creates a store, and it ends when the database at its path is gone or replaced.
- **Continue notices (#356).** Prose that quotes the phrase no longer gets Enter pressed.
- **Tests (#275, #357, #358).** Tests that passed with the named code broken now fail, tests no longer run the real `codex`, and two fixtures no longer outlive their test.

## What was checked

- Full test suite, fmt and clippy on macOS, and CI on Linux.
- `wait` on a real home with 2,000 tasks and 13,000 run files, two 30-second runs, with other work running: 25.1% and 21.7% CPU on v2.15.20, 13.1% and 6.0% on this code. The spread is large.
- Each fix's regression test fails with the fix reverted, repeated by the maintainer for #354, #355, #356 and #359.
- One real round through each tier 1 harness before tagging.

## Not checked

- Any of these fixes in live rounds on Linux, where only CI ran them.
- Continue notices against a real captured screen, and a fix for #359 in a real pane: their tests use fixtures.
- A detached revision whose supervisor fails to spawn; that branch has no fault-injection test.
- Cursor heads and Codex to Cursor handoffs, because Cursor's plan is at 96%.

## Known limits

- `wait` still uses more than the 5% of a core issue #351 suggested.
- Tests still leave `.tmp*` directories behind, and which tests is not known.
- Readiness gate 2-5 (a) stays open: some code has not been read in review, and every review reproduction used a fixture. [The record](../readiness/v1-readiness-checklist-2026-09-14.md) has the rest.
