# brgr v2.12.0

Task worktrees are reclaimed when their result is decided, the way panes
already closed.

## Worktree reclamation

- **On decision.** `accept`, `reject` and `result TASK --ack` remove that
  revision's worktree and its `brgr/task-*` branch when nothing in it would be
  lost. A pane-mode task's worker works in its worktree until its pane closes,
  so the check runs again once the pane has closed. A note goes to stderr
  (`brgr · removed worktree …` or `brgr · kept worktree …: reason`), and the
  decision never fails because of it.
- **What counts as lost.** The checks are the same as `brgr prune --apply`'s,
  with three additions. An untracked harness cache (`.gjc/`, `.commandcode/`,
  `.claude/` and the like) does not keep a worktree. Neither does a change the
  store already holds: when the task sealed a diff with `--capture-diff` and the
  worktree's patch is byte-for-byte that diff. Ignored dependency and build
  directories (`node_modules`, `target`, `.next` and the like) do not keep it
  either. Any other change or ignored file (a `.env`) still keeps it. Only in
  the first two cases is `git worktree remove --force` used.
- **Keeping one.** `--keep-worktree` on `run` or `revise` keeps it, and so does
  `--keep-pane`.
- **`brgr apply` no longer needs the worktree.** It works from the sealed
  patch, the recorded base commit, and the repository recorded at admission.
- `brgr prune` uses the same rules, so worktrees left by earlier versions that
  only hold harness caches or a sealed patch can now be swept.

## Upgrading

Install v2.12.0, then run `brgr integrate codex install` and
`brgr integrate claude install` (the skill mentions `--keep-worktree`). Run
`brgr prune` once to see which older worktrees can go.

```sh
herdr plugin install justn-hyeok/brgr --ref v2.12.0
```

The CLI archive remains unsigned and not notarized.
