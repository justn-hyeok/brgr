# brgr v2.15.22

Fixes for a Codex worker under a custom home, for homes deleted while brgr still ran in them, and for a failure `result --ack` could leave behind. The bundled SQLite moves past RUSTSEC-2026-0459.

## Before you upgrade

- **A Codex pane worker now gets its control home as session config** (`-c shell_environment_policy.set.BRGR_HOME="…"`). Under a custom `--home` or `BRGR_HOME`, its commands, children and debate messages now use that home instead of whatever home Codex's shared daemon carries (issue #362).
- **`brgr result TASK --ack` also acknowledges an earlier failed attempt of the same revision**, such as a spawn failure that was retried. It still never acknowledges a candidate.
- **`brgr doctor` prints its report when the store cannot be opened**, with `store` false and a `store: unavailable` problem, instead of exiting with only an error.
- **The bundled SQLite is newer** (`rusqlite` 0.41.1, `libsqlite3-sys` 0.39.1). The test suite passes on it; no migration was added.

## What changed

- **Codex worker home (#363, issue #362).** See above.
- **Deleted homes stay deleted (#365, #366).** `__notify`, `__notify-workflow`, `__session` and `__supervise` exit without output when their home is gone, instead of recreating it as empty directories. A supervisor that outlives its home no longer writes the worker's result into the deleted path. This was one source of the `.tmp*` directories tests left behind.
- **Retried failures (#367).** See above.
- **`doctor` (#368).** See above.
- **Foreground notice (#369).** A `run --foreground` past eight seconds says it is still running the task, not that it is preparing the worktree.
- **Packaging check (#364).** CI runs `cargo package --workspace --locked`, so a change that builds in the workspace but not as a published crate fails before a release is tagged.
- **SQLite (#383).** See above.
- **Tests (#370 to #380, #384, #386).** A third and a fourth review, the fourth reading all the Rust test code, found tests that passed with the code they named broken. Among them: no test failed when the `--evidence-file` path checks were disabled, and none when a process group kill reached only its leader. Each now fails on that breakage. Tests no longer leave a stub directory per process.

## What was checked

- Full test suite, fmt, clippy and `cargo package` on macOS, and CI on Linux.
- Every fix and test change was checked by breaking the code it guards and watching its test fail, by the maintainer rather than the worker that wrote it.
- One real round through each tier 1 harness before tagging.

## Not checked

- Any of this in live rounds on Linux, where only CI ran it.
- A real store opened by the new SQLite before this Mac's own upgrade.
- The cause of the one test flake fixed in #386, which did not reproduce on macOS.

## Known limits

- Tests still leave a `brgr-fast-script/trampoline-<pid>` file per test process.
- `wait` still uses more than the 5% of a core issue #351 suggested.
- About 28 tests decide an outcome with a fixed sleep or a timer. None fails today; they are left until one does.
- Readiness gate 2-5 (a) stays open: four review rounds have not been checked to cover all production code together, and every review reproduction used a fixture. [The record](../readiness/v1-readiness-checklist-2026-09-14.md) has the rest.
