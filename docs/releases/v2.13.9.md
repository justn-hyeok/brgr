# brgr v2.13.9

Fixes from a review of the four releases of 2026-10-13, and workers that show
their colours.

A Codex worker reviewed `git diff v2.13.4..v2.13.8` read-only. Seven of its eight
findings were reproduced on a clean v2.13.8 build before anything was changed;
each fix below has a test that fails without it.

## Fixes

- **`--include-ignored` could delete files it was never given for.** The choice is
  written down before the decision is recorded, so a pane's own cleanup can honour
  it. A process that died between the two left the note behind, and the next
  decision on that revision, made without the flag, removed its ignored files.
  The note now names its decision and counts only for that one.
- **Reviving a lost run could erase the first worker's worktree.** A lost run's
  worker can outlive its supervisor. A revision shared the task's pid record, hid
  the first worker from `prune`, and `prune --include-ignored` deleted its
  worktree. `brgr revise` now refuses while that worker may still be running and
  names its process.
- **A quoted error could leak into the error memo.** The memo cuts a failure at
  the quoted harness text. It cut at `last stderr:` first, so a quoted stdout
  error that itself contained that phrase left its start in the redacted sample.
  It now cuts at whichever marker comes first.
- **`land --3way` called a refusal a conflict.** When one file conflicted and
  another differed from the index, git applied nothing, but brgr saw the conflict
  line, accepted the result, and wrote a receipt of `applied_with_conflicts` and
  advice to resolve markers that did not exist. A refusal is now an error, and
  only files that actually became unmerged count as conflicts.
- **A failed `apply` blocked its own retry.** After `land` accepted and the write
  then failed, the error named `brgr apply`, which then refused because a
  `started` receipt existed. A failure now leaves a `failed` receipt the retry
  replaces. A `started` receipt, which a crash mid-apply leaves and which may mean
  a partial apply, still blocks.
- **`status --observe` wrote.** It ran the recovery that records a dead
  supervisor's task as lost, so a read changed what the owner would see. It no
  longer runs it.
- **`harness recertify` stranded agent-authored harnesses.** It redrafted every
  harness from help text, which fails for a CLI no recipe describes. A harness
  registered from a manifest is certified again from that manifest.
- **Workers had no colour.** brgr started each worker with an empty environment
  plus a short allowlist, which left out `TERM` and `COLORTERM` although the pane
  has them, so Codex and Claude Code used a reduced palette (Codex lost its blue
  accent; Claude Code fell back from 24-bit colour to 256). The worker now gets
  its pane's `TERM`, `COLORTERM` and `NO_COLOR`. Checked on a real Claude Code
  worker: before, its environment had neither; after, `xterm-256color` and
  `truecolor`.

## Worth knowing

- **Downgrading.** A store that holds results recorded by v2.13.5 or later for
  Cline (`harness_config` as the model's source) cannot be read by v2.13.4 or
  earlier: `result` fails on that row. This release reads an unknown source as
  `unavailable`, so later additions will not do this again.
- Cline's free model has a daily limit; a harness that reports it fails its
  scratch run with `exit code 1`. That is the CLI, not brgr.

## Upgrading

```sh
herdr plugin install justn-hyeok/brgr --ref v2.13.9
```

Existing commands behave as before.

The CLI archive remains unsigned and not notarized.
