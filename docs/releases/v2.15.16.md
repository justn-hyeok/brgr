# brgr v2.15.16

Pane results now name the model a Claude Code or Codex worker really used, Codex workers start reliably on Codex 0.166, and asking for a result too early no longer says the task does not exist.

## What changed

- `brgr result`, `accept`, `reject`, `diff`, `apply` and the other commands that read a result now say `task ... has no sealed result yet` for a task that is still running. They used to say `task ... does not exist` while `brgr status` could see it. A task that really is unknown still says it does not exist.
- `route_observation.model` of a pane run of Claude Code or Codex is filled from the worker's own session log, with `model_source: harness_session_log`. Older builds read the new value as `unavailable`. Anything missing, oversize or odd stays `unavailable`, and other harnesses are unchanged.
- A Codex worker no longer fails with `native TUI is waiting for input readiness` on Codex 0.166. A native TUI counts as ready only after it has looked ready for one second without a break, and a first prompt it does not accept yet is retried for up to twenty seconds. A native worker starts about one second later.
- A Codex head whose first brgr command is `head handoff` is told to run one short `brgr --as SESSION` command first. Codex 0.162 and later show a command's line only after it ends. This explains the failure and gives the remedy; it does not remove the cause.
- `brgr doctor` reports Codex 0.166 as the release the pane trace was checked against (it was 0.160).
- A workflow driver's pid file is written in one step, so `brgr workflow resume` or `cancel` cannot read an empty file and start a second driver.
- Tests that failed under load now wait on events instead of clock windows (issue #224). This does not close #224: the repeated loaded run it asks for has not been done.

## What was checked

- fmt, clippy `-D warnings` and the full workspace tests pass (971 tests before the release commit), and CI passed. The test for the new message was seen failing first.
- A fresh home on Apple Silicon macOS with the release build of `main`, with `BRGR_HOME`, `CODEX_HOME` and `CLAUDE_CONFIG_DIR` in a scratch directory: `integrate claude install`, `integrate codex install`, `harness add` with a real Cursor Agent, and `doctor` printed `ok`. Three real pane tasks from a Claude Code head then ran through `wait` and `accept`; the panes closed, and the worktrees and task branches were gone. A running one answered `result` with the new message. The completion notice reached the head.
- Real pane workers for the model observation: Claude Code (`claude-opus-5-5`) and Codex 0.166.0 (`gpt-6-astra`), one run each. For Codex the observed model equals the requested one, so that run shows the file is found and read, not that the harness chose differently.

What was not checked: a live Codex session whose first brgr command is a handoff, with the new message. A Codex worker without the hook installed, and two Codex sessions in one worktree, are covered by unit tests only.

## Known issue

`accept` printed `brgr cleanup pending: No such file or directory` once in five real pane runs. The decision, pane close, report archive and worktree removal still completed, and it did not repeat. The cause is not known; see issue #265.

## Compatibility

No store schema or config change. `ObservationSource` gains the additive value `harness_session_log`. A script matching `does not exist` for a task that is still running needs the new text.
