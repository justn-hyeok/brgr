# brgr v2.15.11

`brgr status`, `brgr run` and `brgr doctor` put what matters first when you read them on a terminal. `brgr watch` can follow everything you started, and `local.devin` can take a model.

## What changed

- `brgr status` prints a one-line-per-task table on a terminal, and `brgr status TASK` a short key block. `brgr run` prints a receipt whose last line is `task: <id>`. `brgr status --verbose` keeps the full pretty JSON. A pipe, a redirect and `--json` are byte-for-byte what they were.
- `brgr doctor` on a terminal starts with `ok`, or one `needs_attention` line per problem naming the item and the next command it already knows. The exit error names the items too. `--json` keeps every existing field and gains one top-level `problems` array.
- `brgr watch --all` follows this owner's unfinished tasks as they were when it started; tasks created later are not added, and an empty set exits at once. `brgr watch A B C` already took several ids; the help and the shipped skill now say so.
- `local.devin` passes `--model` when the installed CLI documents `--model <MODEL>`, in print mode and in the pane. An older Devin without it keeps the configured-default behavior.
- Tests only: a load flake in `agent_stops_waiting_when_the_workflow_run_is_no_longer_running` has a wider wait and prints node's stderr if it recurs.

## What was checked

- Each change was verified in its own worktree with fmt, clippy `-D warnings` and the full workspace tests, with the diffs read, and CI passed on each pull request.
- In a real terminal (a PTY), `brgr status` printed the table and `brgr doctor` printed its summary above the JSON; piped, both stay JSON.
- A real `local.devin` run with `--model swe-2-high` completed. brgr's launch record holds `--model=swe-2-high`. A `local.devin` certified before this release was refused for `model_select` until `brgr harness recertify local.devin`, as the note below says.
- `brgr watch --all` in a live Herdr pane followed two running tasks, ignored finished ones, and exited with `done` after both results.
- Running `brgr doctor` on a drifted install showed that the integration lines had no command; they now name `brgr integrate codex install` and `brgr integrate claude install`.

What was not checked: that Devin actually answered with the requested model (brgr cannot observe it; only the launch argv is recorded); `brgr doctor` printing `ok` on a healthy install (the Mac used here was not healthy; it is covered by tests only). Several tests fail rarely in full parallel runs and pass alone (`transferred_codex_session_receives_undecided_completion`, two `workflow_runner` tests, `foreground_admission_lock_is_released_before_slow_harness_execution`); their cause is not known.

## Compatibility

No store schema or config change. A `local.devin` certified before this release is refused `--model` until you run `brgr harness recertify local.devin`; brgr prints that command.
