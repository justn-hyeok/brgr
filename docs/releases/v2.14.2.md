# brgr v2.14.2

Handing the owner's head to another session, and owner-side writes that a
displaced session can no longer make.

## A recorded handoff of the head

An owner's head is the session that may read, decide and direct its tasks. Until
now the only way to change it was `brgr bind`, a single unconditional step that
left no record and let the displaced session take the head back. A handoff is now
a record in the store with five commands, each taking a TASK of that owner:

| Step | Command | Who |
| --- | --- | --- |
| request | `brgr head request TASK --to SESSION` | the current head |
| prepare | `brgr head prepare TAKEOVER --goal TEXT` | the outgoing session |
| read | `brgr head show TAKEOVER` | anyone with the store, read only |
| commit | `brgr head commit TAKEOVER` | only the incoming session |
| close | `brgr head retire TAKEOVER` | only the incoming session, after it resumed |

`brgr head abort TAKEOVER --reason TEXT` stops a handoff that has not committed,
and `brgr head status TASK` lists the owner's handoffs.

- The manifest is built from the store: the owner's open task revisions with their
  attempt, the undecided and unacknowledged results, and the unanswered worker
  messages. It holds references only; a result or a decision is never copied or
  restated, and the stored bytes are checked against their digest on every read.
- Nothing moves until the incoming session commits. The commit is one transaction
  that re-checks the binding, raises the epoch by one and requeues unresolved
  completion notices for the new head. A binding that moved since the request makes
  the commit fail and leaves the handoff `prepared`.
- `resumed` is never reported by a caller. The store records it when the incoming
  session performs an owner-side write at the committed epoch (a decision, an
  acknowledgement, a task admission, a reply or cancel, a debate write); `retire`
  is refused until then.
- Repeating a command is safe: a repeated `request` with the same key returns the
  same record, even from the outgoing session after the commit; a repeated `commit`
  does not raise the epoch again; a different destination for the same key is a
  conflict.
- `brgr bind` is refused while an owner has an open handoff, and only one handoff
  may be open per owner. For an owner with no open handoff `bind` behaves as before.

Checked end to end in an isolated home with a real OpenCode worker: the outgoing
session requested and prepared while the worker ran, the incoming session read the
manifest and committed, saw the result that landed during the handoff, was the only
session able to accept it, and retired the handoff after that; the outgoing session
was refused for `accept`, `result --ack` and `bind` throughout.

## Owner-side writes carry a proof

Owner messages and their acknowledgement, cancel, task and revision admission and
the debate writes (`start`, `stop`, `send`, `ack`) now take a proof of the session
and epoch and check it inside the transaction that writes. A takeover that lands
between the CLI's own check and the write can no longer slip a write through, and
after a commit the outgoing session is refused for each of them. Worker-side paths
(a worker reporting, messaging its owner, a nested run) keep the unguarded writes.

## Known limits

- A task revision that has no attempt yet is not named in the manifest; the new
  head sees it in `brgr status`.
- The epoch and session names are cooperative identity checks between harnesses run
  by the same user. They are not a credential and do not authenticate a process.
- This release moves the head; it does not move a worker to another harness or
  change its model, and it does not close the outgoing session. Delivery of
  completion notices to the new head's pane was requeued in the store and checked
  there; it was not driven through two live panes.

## Upgrade

```sh
cargo install --locked brgr-cli --version 2.14.2
herdr plugin install justn-hyeok/brgr --ref v2.14.2
```

No store migration: the new tables are created on first open and an older brgr
ignores them. The macOS archive remains unsigned and not notarized.
