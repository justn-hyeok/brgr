# brgr v2.15.19

Real rounds on macOS found four defects that tests had not, all in how a worker starts or stops. This release fixes them. It also adds `brgr config edit`, and a workflow's `retries` now works in a pane.

This follows v2.15.18 on the same day. The batching rule allows that only for something broken, and the first fix below is that: on a shell asking oh-my-zsh's update question, every worker and handoff failed.

## Before you upgrade

- **A pane agent that stops by itself and writes no report, even after a reminder, now ends `failed`**, not `lost`. A workflow step with `retries` runs it again, so a script may spend more than it did. A pane or process that disappeared stays `lost`.
- **`brgr cancel` and any other close of a stopped worker's pane now stop what ran under it**, such as a background process a Devin worker started. `--keep-pane` is unchanged.
- **brgr may press `n` on oh-my-zsh's update question** in a new pane's shell, and writes it to `runs/<task>-r<rev>.screens.log`.

## What changed

- **New panes (#329).** brgr waits for a new pane's shell to stop drawing before typing into it, up to five seconds, and declines oh-my-zsh's update offer. The offer used to take the command's first letter: `zsh: command not found: odex`.
- **Codex workers (#326, #327).** Under a custom `--home` or `BRGR_HOME`, a Codex worker's commands reached the default home, because Codex's shared daemon lost the setting. Its children were invisible to the owner and outside `cancel`. A stale session in that daemon could also stop it with `CODEX_THREAD_ID and BRGR_SESSION_ID disagree`, or refuse its report seal.
- **Cancel (#328).** A Devin worker's tools survived a cancel when another process closed the pane first.
- **Retries (#325).** See above. Checked live: `die`, then `die~retry1`, then stopped at the limit.
- **`brgr config edit` (#324, issue #308).** Pick harnesses, models and aliases in the terminal.
- **Lost first prompt (#323, issue #316).** An agent never seen working gets the prompt again, not an order to report.
- **Guidance (#330).** The skill says which feature fits which job, and `brgr head --help` says which subcommands an owner runs.

## What was checked

- Full test suite, fmt and clippy on macOS, and CI on Linux.
- [Debate, handoff and delegation on macOS](../evidence/debate-handoff-delegation-macos-2026-11-05.md): three debates, delegation and cancel, three handoffs and one automatic handoff, in real panes.
- One real round through each tier 1 harness before tagging.

## Not checked

- oh-my-zsh's offer being declined live. The offer had already been answered when the fix ran, so the key press has only its unit test.
- A usage figure from a real plan driving a conditional handoff; the test wrote the figure.
- Cursor heads and Codex to Cursor handoffs, because Cursor's plan was at 96%. None of the macOS rounds above used Cursor.
- These fixes in live rounds on Linux, where only CI ran them. A real machine sleep.

## Known limits

- A pane run's deadline counts awake time while its supervisor lives. Recovery after the supervisor died, and the time remaining in `status --tree`, use the wall clock.
- A tool that a Codex worker runs lives in Codex's shared daemon, so a cancel cannot reach it.
- A Codex head under a custom home must pass `--home` itself. A Codex worker in a workspace that is not a brgr worktree is not covered by the home fix.
- In one debate, Codex took 115 seconds to send its first question. The cause was not found.
