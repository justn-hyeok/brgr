# brgr v2.15.10

Dynamic Workflows ships. A node script drives workers; brgr journals every step so a dead driver resumes without creating a second task.

## What changed

- `brgr workflow init` writes `brgr-workflow.mjs`, `brgr-workflow.d.mts` (TypeScript declarations, no build step) and an example. `brgr workflow run SCRIPT` starts a detached driver; `workflow resume`, `status`, `cancel` inspect and control it.
- The SDK has `agent()`, `parallel()` and `pipeline()`. `pipeline()` runs stages in order, passes each sealed result to the next, and stops at the first outcome that is not `completed`.
- Per step: `deadline` (1 to 86400 seconds, measured from the task's first attempt in the store) and `retries` (0 to 3). Only a sealed `failed` outcome is retried; `lost`, `cancelled`, a deadline cancel and unknown outcomes never are. Each retry is its own journaled step, so a resumed run never launches an attempt twice.
- `timed_out` is true only when the SDK's own deadline cancel is the sealed outcome. An owner's `brgr cancel` after the deadline is not reported as a timeout.
- Steps open TUI workers beside the head's pane when the run started from a verified Herdr pane; otherwise use `mode: "headless"`.
- A new task's objective is capped at 256 KiB and its acceptance criteria are bounded (32 criteria, 4096 bytes each, 64 KiB total). The default criterion no longer copies a long objective. Tasks already in a store still load.
- Tests only: a retry-resume test no longer races the supervisor, and a flaky pane accept test now prints what was left behind if it fails again.

## What was checked

- Every slice was verified in a separate worktree with fmt, clippy `-D warnings` and the full workspace tests, and the diffs were read.
- A live two-stage `pipeline()` with `deadline` and `retries` ran in a real Herdr pane with a real harness and completed.
- The declarations pass `tsc --strict` (5.6.3) under nodenext and bundler resolution.

What was not checked: a workflow with a `retries` step that really fails in a live pane; whether `pane_mode_runs_the_agent_in_a_pane_and_seals_its_report` still fails rarely. It failed once and did not reproduce in 60 loaded runs.

## Compatibility

No store schema or config change. Existing tasks load. A workflow journal written by a development build without `retries` keeps the same step digests.
